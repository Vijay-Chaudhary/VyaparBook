# UI Backlog

Lightweight tracking for frontend work — bugs, features, and UI polish across the
Blade shell and the React islands under `/app/*`. This doc is the fast, in-repo
capture point; anything that needs assignment, discussion, or a milestone should
graduate to a **GitHub issue** on `Vijay-Chaudhary/VyaparBook` under the matching
label (`bug`, `feature`, `ui`).

## Conventions

- **ID** — `B-01` (bug), `F-01` (feature), `U-01` (ui polish). Never reuse an ID.
- **Status** — `todo` · `in-progress` · `blocked` · `done`. Keep `done` rows for one
  release, then prune.
- **Area** — where it lives, e.g. `khata`, `stock`, `onboarding`, `billing`,
  `platform-console`, `offline/sync`, `shell`.
- **Issue** — link the GitHub issue number once one is opened (`#12`), else `—`.
- Newest items go at the top of each table. One line per item; put detail
  (repro steps, screenshots, acceptance criteria) in the linked GitHub issue.

| F-12 | done | khata/sales | Negotiated sale pricing + ledger line items. A salesman can now change a line's price in the field: the rate prefills from the pack default, re-fills when the product changes, and each line shows its own subtotal. **Tax on the client, authority on the server** — `rate` is client-supplied but `list_rate` (what list price WAS that day) is always server-authored, so a phone cannot claim it sold at list while charging less; `sale_lines.list_rate` is nullable and never backfilled, because inventing a historical default would make discount analysis wrong while looking authoritative. Price is bounded by a **cost floor** = `default_cost_price` ?? `base_cost_per_kg × weight_kg` ?? unbounded, enforced in BOTH runtimes (`App\Pricing\PriceFloor` and `offline/pricing.js`) against one shared case table — duplicated deliberately so the phone can block a below-cost price while the customer is still there, with `rate == floor` allowed and derived floors rounded UP. Fixed a real bug found on the way: a below-floor line used to 422 an **entire sync batch**, breaking `SyncController::push()`'s own documented promise that one bad mutation is reported, never fatal — it now parks that item alone. Also batched the per-line pack fetch (a 6-line sale went from ~18 queries to 3) and moved the floor error into `lang/{en,hi}/sales.php`, since `__()` with a literal English string silently renders English in Hindi. The customer ledger now shows what was sold under each sale, at the price charged, from cached `sale_lines` for synced sales and the outbox payload for queued ones. See spec `docs/superpowers/specs/2026-07-25-negotiated-sale-pricing-design.md` and plan `docs/superpowers/plans/2026-07-25-negotiated-sale-pricing.md`. | — |
| F-11 | done | beats/offline | Salesman beat planning (PRD Phase 3) — the last field-facing Phase 3 item. A **beat** is a named set of customers worked on fixed weekdays ('Rampur runs Mon + Thu'), which is how FMCG distribution schedules and repeats forever with no calendar to maintain — an unmaintained calendar leaves a salesman staring at an empty screen that reads as broken. Owner plans on a new Blade `/beats` (create, weekdays, assign a member, tick customers in call order, archive); membership is **checked not trusted**, so an unowned user id silently unassigns rather than being accepted. `beats`/`beat_customers` are the **first new offline-synced entities since the core**: they carry `sync_seq` and stream down the existing delta pull, keyed on `id` (not `uuid`) because they are **server-written only** — the phone reads them and never writes them, so there is no push path, no idempotency key and no conflict rule in the field. A salesman's pull returns **only beats assigned to them**, with membership rows following their beat so nothing on the device dangles; unassigned beats stay visible since a small shop's owner often works a route. Dexie schema v5 + `offline/beats.js` answers 'who am I calling on today?' from the last successful pull, so it works with no signal. Archive rather than delete, so devices learn to drop it. Recording visits from the field is deliberately a later phase — it needs the push path, idempotency and conflict rules the sale/payment path took real care over. See spec `docs/superpowers/specs/2026-07-25-beat-planning-design.md`. | — |
| F-10 | done | invoicing | GST invoicing (PRD Phase 3) — issue a numbered tax invoice for a sale, with a print view. **Prices are treated as GST-inclusive and tax is extracted, never added**: `taxable = total ÷ (1 + rate/100)`, tax by subtraction, so `taxable + cgst + sgst == sale.total` **exactly** and khata/outstanding/cash-flow are untouched — issuing an invoice can never change what a customer owes (asserted). Invoicing is an **explicit online act**, not automatic at sync, which is what makes gapless numbering safe: an offline device never allocates a number. Numbers come from an `invoice_counters` row locked `FOR UPDATE` (not `MAX(seq)+1`, which two concurrent requests would read identically), series per **April–March financial year**, format `2026-27/0001`. Invoices are **immutable snapshots** — the lawful exception to PRD §9 — so a later product-rate change cannot alter a filed document. Intra-state only: **CGST + SGST** at half the rate each, odd paisa to CGST; no IGST and therefore no state field on the offline-synced `customers` table. Buyer GSTIN is captured per-invoice for the same reason. GST columns on `products` are server-side only (absent from `$fillable`), set from a new Blade `/gst` screen, so the sync payload and Dexie schema are unchanged. Refuses: a second invoice per sale (unique `sale_id`), a voided sale, and a shop with no GSTIN. New `invoices`/`invoice_lines`/`invoice_counters` (RLS + app scope, registered in DPDP export/erase). See spec `docs/superpowers/specs/2026-07-25-gst-invoicing-design.md`. | — |
| F-09 | done | reports/stock | Finished-goods inventory (PRD Phase 3) — stock previously meant **raw materials only** (`stock_movements.raw_material_id` is non-nullable), so besan had a ledger and the namkeen made from it had none. New derived-only `FinishedGoodsService` (no new tables, no migration): produced = Σ `production_batches.output_kg`, sold = Σ (`sale_lines.qty` × `pack_sizes.weight_kg`), on-hand = the difference, per product since inception, bcmath at scale 3. Returns and voids are negative-qty lines so they **self-net** — no row excluded or mutated. Tracked by **weight, not pack count**: production records bulk kg and packing happens on the way out, so this works retroactively over all existing history, needs no new owner input, and leaves the offline React sale/production screens and Dexie schema untouched. Cost of that choice: it reports "12.4 kg", not "62 pouches" — pack-level counting is deferred until we know whether shops pre-pack. Negative on-hand is **shown in the danger colour, not clamped**: it means unrecorded production or a mis-keyed batch, which is exactly what the ledger exists to reveal. New dashboard table + en/hi keys; additive field on `DashboardReport`. No reorder threshold — `products` has no reorder level and inventing one would need a migration this phase does not require. See spec `docs/superpowers/specs/2026-07-25-finished-goods-inventory-design.md`. | — |
